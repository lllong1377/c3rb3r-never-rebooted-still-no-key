# 02 · 密钥扫描：怎么把一个「没找到」变成可信结论

这篇是整个仓库最想说的部分。本案的结果是**没找到密钥**，而「没找到」本身说明不了什么——可能是真的没有，也可能是扫描方法写错了、路径指错了、镜像被截断了。下面记录我们怎么证明这个「没找到」不是扫错。

## 一、被找的东西长什么样

每个文件用一把独立的 ChaCha8 密钥加密，这把密钥本身被**会话主密钥**用 AES-256-CBC 包在文件页脚开头 48 字节：

```
rec           = file_key(32) | nonce(8) | nonce(8)      # nonce 写了两遍
footer[0:48]  = AES-256-CBC_encrypt(rec, key=master[16:48], iv=master[0:16])
master        = iv(16) | aes_key(32)                    # 共 48 字节
```

会话主密钥只存在于加密进程的内存里，由全局指针引用。这也是为什么上游案例能靠「冻结进程 + 读内存」直接取出来。

## 二、不需要 IV 的 64 位校验

已知页脚 `footer[0:48]`，对任意候选 32 字节 `k`：

```
T  = LE64(footer[16:24]) XOR LE64(footer[24:32])
P3 = AES256_decrypt_block(k, footer[32:48])
((P3 >> 64) XOR (P3 & (2^64 - 1))) == T    →  k 就是 AES 密钥
```

推导：`P3 = D_k(C3) XOR C2`，而明文第三块恰好是 `nonce || nonce`，所以低 8 字节等于高 8 字节。把 `T` 提到常数项，就等于只解密一个 AES 块、做一次异或和比较，**不需要 IV**——因此可以拿内存里任意 48 字节窗口直接试。

误报率：64 位校验，13.5e9 个候选的期望误报数约 `7e-10`，实际等于零。命中后再用 IV 做一次完整 CBC 解密复核（`tools/scan_master.py` 里的 `full_check`）。

## 三、「没找到」必须先通过自检

这是本仓库最有价值的一条经验，也是给上游仓库提的建议之一：**扫描器必须先证明自己能找到，才有资格宣布没找到。**

`tools/scan_master.py --selftest` 做三件事，用的都是正式代码，不是另写的测试小程序：

1. 随机生成 48 字节 master，用它包一条合法的 48 字节记录，得到页脚前三块；
2. 生成一片随机数据，在**随机偏移**把 master 原样埋进去（不做对齐），全偏移扫描，要求**命中恰好 1 处且偏移与密钥都正确**；
3. 空白对照：同一片随机数据不埋密钥，要求 **0 命中**。

```
== 自检 ==
数据 4.0 MiB，主密钥埋在偏移 0x9244f，步长 1
扫描耗时 13.2 s（0.3 MB/s），命中 1 处
PASS  命中唯一且偏移、密钥都对
PASS  完整 CBC 复核取出 file_key/nonce 一致
PASS  空白对照 0 命中
== 自检通过 ==
```

自检用的是 `--no-prefilter` 等价路径，避免前置过滤偶然把真密钥滤掉导致自检假失败。

## 四、本案的扫描参数与结果

| 项目 | 值 |

| 总量 | **13.5 GiB** |
| 步长 | **1 字节**（全偏移，不做 16 字节对齐） |

| 耗时 | 1,591 s（约 26.5 分钟） |

扫描范围覆盖了物理内存的全部 513 个段和全部 6 个 zram 镜像，没有任何区间被跳过。

## 五、为什么必然扫不到

时间线是关键：

- 加密在 `2026-10-28 12:28` 结束（4,085 个文件在同一分钟内落盘），此后进程退出；
- 内存镜像采集于 `2026-10-29 18:53:14`，**相隔 30 小时 25 分**；
- 期间机器一直在正常提供服务（容器、下载、Web 服务都在跑），空闲页被持续复用。

上游作者逆向样本时发现，样本在退出路径 `0x438b5e` 处会**主动清零那 48 字节密钥缓冲**。也就是说不是「可能被覆盖」，而是设计如此。进程退出即密钥消失，30 小时的差距毫无悬念。

## 六、读你的 NO_MATCH：四种解释

拿到 NO_MATCH 时，按顺序排除：

1. **采样窗口没赶上。** 最常见。查加密完成时间与采集时间的间隔，以及采集时 `/proc` 里还有没有可疑进程。间隔以小时计，基本可以确定是这一类。
2. **样本不同。** 同一波事件里会话标记不同就是不同样本/不同会话（本案 `038c0ac9`，上游案例一 `ce35a593`、案例二 `883c0309`、另一独立案例 `6d147f60`）。页脚布局也可能不同，用别人的密钥必然失败。
3. **镜像不全。** 换页设备没取（只取了 `/dev/md1` 而漏掉 zram）、镜像被截断、LiME 段长算错——这些都会让扫描范围少一大块。用 `lime_parse.py` 的字节核对核一遍。
4. **扫描器本身有问题。** 用 `--selftest` 排除。

前三条用证据排除，第四条用自检排除。四条都排除了，「没找到」才成立。

## 七、性能参考与建议

- 单核约 0.3–0.4 MB/s，20 核约 7–8 MB/s；13.5 GiB 约半小时。这一步是 CPU 密集，别在 NAS 上跑，拉回电脑跑。
- 想先快速摸底可以 `--stride 16`（快 16 倍），但它只检查 16 字节对齐的起点。堆上 `malloc` 的 48 字节通常是对齐的，所以粗扫合理；要下「没有」的结论仍建议全偏移跑一遍。
- `--no-prefilter` 关掉前置过滤，慢约 10 倍，只在怀疑漏检时用。前置过滤会跳过「像文本」和「像零区」的候选，理论上存在把真密钥滤掉的可能（概率约 1e-7 量级）。
