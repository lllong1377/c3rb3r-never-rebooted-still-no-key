# 01 · 不关机采集：AVML 在 DSM 实机上能跑，但有前提

本篇记录怎么在一台**已经中招、仍在运行、且目标卷已经被写满**的 DSM 机器上，把物理内存和交换区完整取下来。结论先放这里：可行，本案 57 秒取完 7.92 GiB，未崩溃、未重启。

## 为什么不用「冻结进程 + 读 /proc/PID/mem」

上游两个成功案例走的是这条路：发现时加密进程还活着 → `kill -STOP` 冻结 → 从 `/proc/PID/mem` 导出可写区 → 按全局指针取 48 字节会话主密钥。这条路更快、更准，但它有一个硬前提：**进程必须还活着**。

本案的情况是另一种：发现时加密已经结束约 30 小时，`/proc` 里没有任何可疑进程，只剩下已经加密的文件。此时唯一还能试的就是整机内存取证。所以两条路不是替代关系，是「赶上了」和「没赶上」的区别。

判断标准很简单，一条命令：

```sh
ls -l /proc/*/exe 2>/dev/null | grep deleted
```

- 有输出，且指向类似 `libgld` / `qnetd` 的路径 → 进程还在，先 `kill -STOP`，走上游的路，别重启、别 kill -9。
- 没输出 → 密钥大概率已经没了（见 [02-key-scan.md](02-key-scan.md)），整机采集只作为下限手段和留证。

## 采集前的三个前提

**一、输出卷必须有空间，而且不能是被写满的那一个。**
勒索软件会把某个卷写到 0 可用。本案 `/volume1` 可用 0 字节，而 `df` 显示的数据块是 100% 占满（`btrfs filesystem usage`：`Data,single: Size 210.91GiB, Used 210.91GiB`）。镜像不能落在 `/volume1`，本案落在 `/volume2`（机械盘）。

**二、不要重启。** 重启会清空物理内存；对本案这种「进程早已退出」的情况重启无害，但对「进程还活着」的情况重启等于永久放弃。

**三、不要对原卷做写操作。** 采集只写输出卷。

## 采集命令

用 AVML v0.21.0 静态二进制（x86_64，7,581,584 字节）：

```sh
./avml --format lime --output /volume2/ir/memdump.lime
```

本案实测：

| 项目 | 值 |
|---|---|
| 输出大小 | 8,504,266,784 字节（7.92 GiB） |
| 耗时 | 57 s（机械盘，约 149 MB/s） |
| sha256 | `cb7d1575ba18a5b7ca0360728422b11fdffa87622eb7d095806c9a17288457df` |
| 副作用 | 无崩溃、无重启，业务进程未中断 |

`tools/capture-live.sh` 把「空间检查 → 可疑进程快照 → 采集 → 校验 → 交换区采集」串在一起，可以直接跑。

## 镜像是什么格式：LiME 段结构

AVML 的 `--format lime` 不是裸内存，而是「32 字节段头 + 段数据」重复拼接：

```
偏移 0    magic  u32 LE = 0x4C694D45   （落盘字节序是 45 4d 69 4c）
偏移 4    version u32  = 1
偏移 8    s      u64   物理起始
偏移 16   e      u64   物理结束（含）
偏移 24   reserved 8 字节，全 0
段长 = e - s + 1
```

两个必须记住的坑：

1. **段长是 `e - s + 1`，不是 `e - s`。** 差一个字节，按 `e-s` 算会从第二段开始全部错位，看起来像镜像损坏。
2. **头是 32 字节，不是 24。** 我们第一版按 24 字节解析，结论全错，直到逐段比对才发现。

`tools/lime_parse.py` 会按上面的规则走完全部段，输出段数、捕获量、物理范围、段间空洞，并核对「捕获 + 头部开销 = 文件长度」，以此确认镜像没被截断：

```
段数      513    头部开销 16416 字节
捕获内存  7.920 GiB
物理范围  0x1000 .. 0x26effffff
段间空洞  8 处，合计 1.814 GiB（PCI/保留区，正常）
字节核对  捕获 + 头部 = 文件长度，无残余
```

段间空洞不需要担心，那是 PCI 地址空间和保留区，物理上就不存在对应内存。

## 交换区：真正存数据的是 zram，不是 /dev/md1

DSM 的 `/proc/swaps` 里常能看到 `/dev/md1` 之类的分区交换，但它的 `Used` 可能是 0——真实的被换出页面在 zram 里（压缩内存盘），本案有 6 个：

```
/dev/zram0  ...  /dev/zram5   各 812,028 KB，合计已用约 631 MB
```

要取的是解压后的页，直接 `dd if=/dev/zramN`，每个 831,520,768 字节。如果只看 `/dev/md1` 使用量是 0 就跳过，会漏掉全部交换内容。

本案的回报正好在这里：zram2 完整保留了投放脚本正文，因此拿到了 C2 地址、落地文件名、启动参数和持久化路径（见 [04-iocs.md](04-iocs.md)）。**但密钥不在里面。**

## 传输与权限

采集文件由 root 写出，默认 `600`，用普通账号 `scp` 会失败。先 `chmod 444`（目录要可进入），再拉走。另外 DSM 的 SSH 默认启用 SFTP 受限主目录，`scp` 会报 `remote mkdir: No such file or directory`，加 `-O` 走旧式协议即可：

```sh
scp -O user@host:/volume2/ir/memdump.lime ./
```

## 常见误区

- 「机器一直开着，内存里就还有密钥」——错。见 [02-key-scan.md](02-key-scan.md)：判断依据是进程是否存活，不是机器是否重启。
- 「镜像取下来就能解密」——不能。镜像只是取证材料，能不能出密钥取决于第 02 篇的扫描结果。
- 「先把可疑进程 kill 掉再说」——`kill -9` 会让密钥彻底消失，要停就 `kill -STOP`。
