# 03 · 页脚清点：不解密也能算出「还有多少东西可用」

被加密之后，最实际的问题不是「能不能全解回来」（多半不能），而是**这份数据里到底还剩多少可用的字节**。答案写在每个文件的 588 字节页脚里，不需要密钥就能读。

## 页脚格式

偏移相对页脚起点，页脚位于文件末尾，紧接在加密后的正文之后。

| 偏移 | 长度 | 含义 |
|---|---|---|
| 0 | 48 | AES-256-CBC 包裹的 `file_key(32) + nonce(8) + nonce(8)`，**加密** |
| 48 | 520 | 其余字段，含一段 304 字节的公钥包裹区（对恢复无用） |
| 568 | 4 | 会话标记，每次运行不同，同一会话内一致 |
| 572 | 1 | 文件模式：`0x24` 整文件 / `0x25` 分段 / `0x26` 仅前 1 MiB |
| 573 | 1 | 分段参数 pct（仅 `0x25` 有意义） |
| 574 | 1 | 加密模式：`0x20` 真加密 / `0x21` 诱饵（拿到密钥也解不开） |
| 575 | 1 | 保留 |
| 576 | 4 | 未确认含义，本案实测 `82 a9 03 00` |
| 580 | 8 | 原始大小（u64 LE），不含页脚 |

一致性检查：`osz + 588 == 文件大小`。不等就说明有追加数据或被截断。

## 三种模式决定密文覆盖范围

- **`0x24` 整文件**：整个正文都是密文。**零明文可用**。本案所有 SQLite 数据库都是这个模式。
- **`0x26` 仅前 1 MiB**：只加密开头 1 MiB，其余明文原样保留。小文件基本全毁，大文件损失有限。
- **`0x25` 分段**：按 pct 在头、中、尾各加密若干段。pct=10 时每段占 4%，共 3 段；pct=50 时共 5 段。**明文中段还在，但文件结构被切断。**

## 本案清点结果

对 3 个卷做全量页脚解析（`tools/footer.py --dir`）：

| 指标 | 值 |
|---|---|
| 加密文件 | **892,384** 个 |
| 原始总量（去掉页脚） | 约 3.57 TiB |
| 密文覆盖 | 约 **470 GiB（12.9%）** |
| 残存明文 | 约 **3.11 TiB（87.1%）** |
| 分段模式主力 | pct=10 的大文件约 6,965 个，原始量约 3,510 GiB |

乍看 87% 是好消息，实际不是。

## 为什么 87% 明文不等于 87% 可恢复

**一、明文的位置恰好是「最不该缺的那部分」。** 分段模式加密的是头、中、尾。文件头是格式标识和元数据（PDF 的 xref、Office 的目录、图片的尺寸与色表、视频的 moov），丢了头就打不开；中段丢了可能只是花屏，但头一旦没了，任何解析器都拒绝读取。

**二、容器类文件不能靠拼。** ZIP/Office/视频容器靠索引结构定位成员，索引被切碎之后，「把明文段拼回去」只能靠启发式扫描，出来的是内容片段，不是原文件。上游其他案例里这类重建的成功率，取决于文件类型和碎片完整度，不能当作普遍结论。

**三、数据库是最坏的情况。** SQLite 按页组织，页号写在每个页头里，靠 B-tree 串联。本案 10 个数据库全是 `0x24` 整文件模式：

```
会话标记 038c0ac9   模式 0x24 (full)   pct=0   加密模式 0x20
密文范围 16,920,576 字节（整文件）   残存明文约 0.0%
```

一个明文块都没有，连「按 `SQLite format 3` 页头雕刻」都无从下手。

## 也别指望从空闲块里捞旧数据

加密器改写文件会走 btrfs 的写时复制：旧数据块被释放，然后在后续写入中被重新分配。本案卷状态是：

```
Data,single: Size 210.91GiB, Used 210.91GiB
Device unallocated: 100.00MiB
```

数据块 100% 占满，没有任何空闲区。也就是说被释放的旧明文块已经全部被吃掉了，对裸设备做页雕刻没有物理基础。**如果卷还有大量空闲块，这条思路才值得一试**——先看 `btrfs filesystem usage` 再决定。

## 这份清点有什么用

1. **设定预期**：先知道哪些目录还有明文、哪些已经彻底没了，避免在必输的地方耗时间。
2. **挑恢复顺序**：`0x26` 和 `0x25` 的大文件先救，`0x24` 的放最后（除非拿到密钥）。
3. **判断是否值得付费/求助**：如果核心资产全在 `0x24` 文件里，任何宣称「恢复 85%+」的第三方服务都不适用于你。

```sh
python3 tools/footer.py --dir /volume1/share --csv triage.csv
python3 tools/footer.py /volume1/share/x.db.L0CK3D      # 单文件
```

输出会按模式给出文件数、原始量、密文量、密文占比，并统计会话标记个数。出现多个标记说明经历过多次加密或混入了别的机器数据——这种情况需要分别处理。
